# ExecuTorch on STM32F407 — Bare-Metal Getting Started Guide

Running PyTorch inference on a Cortex-M4 microcontroller with no OS, using
ExecuTorch (release/1.2) and the STM32F407VG Discovery board.

For one-time environment setup (installing prerequisites, cloning and
building ExecuTorch for host and Cortex-M4), see
[README-installation.md](README-installation.md). This document assumes that
setup is already done.

```
└── executorch-build/
    ├── host/                          # ExecuTorch built for Linux
    └── cortex-m4/                     # ExecuTorch built for STM32

first_et_project/                      # this project
├── CMakeLists.txt
├── CMakePresets.json
├── stm32f407.ld
├── startup_stm32f407.s
├── arm-none-eabi.cmake                # copy to executorch toolchains dir
├── models/
│   ├── export_model.py                # simple model in pytorch
│   └── tiny_model.pte                 # generated by export_model.py
├── src/
│   ├── main.cpp                       # STM32 inference runner
│   ├── main_host.cpp                  # Linux inference runner
│   └── syscalls.c                     # newlib stubs
└── build/
    ├── host/                          # cmake --preset host output
    └── stm32/                         # cmake --preset stm32 output
```

Update `CMakePresets.json` if your ExecuTorch paths differ from
`~/executorch/executorch-build/{host,cortex-m4}`.

### Relationship to `../first_embedded`

`stm32f407.ld`, `startup_stm32f407.s`, and `src/syscalls.c` are based on the
same files in the sibling `../first_embedded` project, which has no
ExecuTorch dependency and serves as the plain bare-metal baseline. They are
**not** identical — this project layers on the additions ExecuTorch needs:

- **`stm32f407.ld`** — adds the `CCMRAM` memory region and a `.ccmram`
  (`NOLOAD`) output section, used for ExecuTorch's `method_pool` /
  `planned_pool` scratch buffers (see `src/main.cpp`) to keep them out of
  the main 128KB SRAM.
- **`startup_stm32f407.s`** — adds a zero-fill loop for `.ccmram` in
  `Reset_Handler`, run right after the `.bss` zero loop. (While merging
  these files, a prior version of this loop was unreachable — its `bge`
  branch was skipped over by the preceding loop's exit — so the CCM RAM
  buffers were silently left uninitialized. The fix chains the loops
  correctly: `.bss` zero → `.ccmram` zero → `init_newlib`.)
- **`src/syscalls.c`** — adds the byte-safe `memcmp`/`memcpy`/`memset`
  overrides (Gotcha 6), the `snprintf`/`vsnprintf` overrides (Gotcha 16),
  and the `et_pal_emit_log_message` no-op stub (Gotcha 8), none of which
  are needed by the plain baseline in `first_embedded`.

If you update the shared baseline in `first_embedded`, re-apply these three
deltas rather than copying its files over wholesale.

## 2. Export the Model

```bash
source ~/executorch/et-env/bin/activate
cd first_et_project
python3 models/export_model.py
```

Expected output:
```
Exported to: models/tiny_model.pte
Model size:  1688 bytes
Ops in exported graph:
  dim_order_ops._to_dim_order_copy.default
  aten.mul.Tensor
  ...
Sanity check PASSED
```

The `.pte` file contains both the FlatBuffer program description and a
constant segment with model weights/constants at the end of the file.

### Turning the `.pte` into a C header (`xxd`)

The STM32 firmware can't load a file off a filesystem, so the `.pte` bytes
are embedded directly in the binary as a C array via `xxd -i`.

**This step is done automatically** by `CMakeLists.txt` at configure time —
you don't need to run `xxd` by hand for a normal build (see
[Section 4](#4-build-flash-and-debug-on-the-board)). It runs `xxd -i` on
`models/tiny_model.pte`, post-processes the output to add
`__attribute__((aligned(16)))` (required by the FlatBuffer parser — see
[Gotcha 7](#gotcha-7-model-array-must-be-16-byte-aligned)),
and writes the result to `${CMAKE_BINARY_DIR}/tiny_model_pte.h`.

If you ever need to generate it manually (e.g. to inspect the array or debug
the build), reproduce what CMake does:

```bash
# Must run from inside models/ — xxd -i uses the input filename (with any
# path) as the C variable name. Running from the project root would produce
# a mangled name like `models_tiny_model_pte` instead of `tiny_model_pte`.
cd models
xxd -i tiny_model.pte > tiny_model_pte.h
cd ..
```

Then manually edit the generated header to add the alignment attribute:

```c
// before:
unsigned char tiny_model_pte[] = { ... };
unsigned int tiny_model_pte_len = ...;

// after:
__attribute__((aligned(16))) const unsigned char tiny_model_pte[] = { ... };
const unsigned int tiny_model_pte_len = ...;
```

uses the same runtime and kernels (in a Linux process instead of bare-metal)
and is much faster to iterate on.

## 4. Build, Flash, and Debug on the Board

### Build

```bash
cmake --preset stm32
cmake --build --preset stm32
```

`CMakeLists.txt` runs `arm-none-eabi-size` automatically as a POST_BUILD
step, so memory usage prints in the terminal as part of the
`cmake --build --preset stm32` output above. Should fit in 1MB flash and
128KB RAM:

```
   text    data     bss     dec     hex filename
 303549     500   82816  386865   5e731 build/stm32/firmware.elf
```

To check it again later without rebuilding, run it manually:

```bash
arm-none-eabi-size build/stm32/firmware.elf
```

If `.text` exceeds 1MB (1048576 bytes), you have too many ops linked. Check
that `executorch_selected_kernels` is built and that `--whole-archive` only
wraps that library, not all of `portable_kernels` (see
[Gotcha 9](#gotcha-9---whole-archive-required-for-op-registration)
and
[Gotcha 10](#gotcha-10-use-executorch_selected_kernels-not-portable_ops_lib)).

### Flash with OpenOCD

```bash
openocd \
  -f interface/stlink.cfg \
  -f target/stm32f4x.cfg \
  -c "program build/stm32/firmware.bin 0x08000000 verify reset exit"
```

### Debug with GDB

Inference results land in `volatile` variables (`correct`, `results`) that
are inspected at the final `while(1)` in `src/main.cpp`.

**Terminal 1** — start the OpenOCD GDB server:
```bash
openocd -f interface/stlink.cfg -f target/stm32f4x.cfg
```

**Terminal 2** — connect GDB and inspect the results:
```bash
gdb-multiarch build/stm32/firmware.elf
```
```
(gdb) target remote :3333
(gdb) monitor reset halt
(gdb) load                    # flash the firmware
(gdb) monitor reset halt
(gdb) break src/main.cpp:160  # adjust to your final while(1) line
(gdb) continue
(gdb) print correct           # should be true
(gdb) print results           # should be {3, 5, 7, 9}
```

### Diagnosing faults

The `Default_Handler` in `startup_stm32f407.s` captures fault context. When
stopped there, in GDB:

```
(gdb) info registers r1 r2 r3
```

- `r1` = PC at fault (where the crash happened)
- `r2` = LR at fault (who called the faulting code)
- `r3` = CFSR value (fault type):
  - `0x00000001` = IACCVIOL (instruction access violation)
  - `0x00020000` = UNALIGNED (unaligned memory access)
  - `0x00080000` = NOCP (FPU not enabled — see
    [Gotcha 1](#gotcha-1-fpu-not-enabled--nocp-fault))
  - `0x00010000` = UNDEFINSTR (undefined instruction)

```bash
# Map PC to source line
arm-none-eabi-addr2line -e build/stm32/firmware.elf 0x<r1_value>
```

## 5. Bare-Metal Gotchas Reference

These are the issues encountered getting ExecuTorch running on bare-metal
Cortex-M4. Each took significant debugging to identify.

---

### Gotcha 1: FPU Not Enabled → NOCP Fault

**Symptom:** Program crashes deep inside kernel math code with
`Default_Handler`. CFSR = `0x00080000` (NOCP = No Coprocessor).

**Cause:** The Cortex-M4 FPU is disabled by default after reset. Any
floating-point instruction (`VADD`, `VMUL`, `VLDR`, etc.) triggers a
UsageFault before any computation happens.

**Fix:** Enable the FPU at the very first instruction in `Reset_Handler` by
setting CP10 and CP11 to full access in the CPACR register (address
`0xE000ED88`):

```asm
Reset_Handler:
    ldr r0, =0xE000ED88
    ldr r1, [r0]
    orr r1, r1, #(0xF << 20)
    str r1, [r0]
    dsb
    isb
    ; ... rest of startup
```

This must be the absolute first thing in Reset_Handler — before data copy,
before BSS zeroing, before everything.

**Also required in CMake:** Use `-mfloat-abi=hard` and `-mfpu=fpv4-sp-d16` to
generate hardware float instructions. Without `-mfloat-abi=hard`, the
compiler uses software float emulation (slow) and never exercises the FPU,
masking this issue but producing 10x slower inference.

### Gotcha 2: .got Must Come Before .data* in Linker Script

**Symptom:** Program loads and parses successfully but crashes inside
`memcmp` during `ExtendedHeader::Parse`. GDB shows `s2` (the address of
`ExtendedHeader::kMagic`) is a garbage value like `0x2f656d69` instead of a
valid flash address (`0x0803xxxx`). The GOT contents at runtime contain ASCII
text strings instead of addresses.

**Cause:** The Global Offset Table (GOT) contains absolute addresses for
global/static variables. It is a section in `.data` that must be copied from
flash to RAM. If `.got` is placed after `.data*` in the linker script, the
GOT occupies a RAM address higher than `_sdata`, and some other data
overwrites it (or the copy loop misses it). The result is that constexpr
static variables accessed through the GOT point to garbage.

**Fix:** In the linker script, place `.got` and `.got.plt` FIRST inside the
`.data` section:

```ld
.data :
{
    _sdata = .;
    *(.got)       /* MUST be first */
    *(.got.plt)
    *(.data*)
    _edata = .;
} > RAM AT > FLASH
```

This ensures the GOT is at the start of the data region and is covered by the
Reset_Handler's flash-to-RAM copy loop.

### Gotcha 3: __libc_init_array Must Be Called

**Symptom:** `Program::load` succeeds, `Program::load_method` returns error
code `0x14` (`OperatorMissing`). All operator lookups fail.

**Cause:** ExecuTorch registers kernels into a global registry using C++
static initializers. The registration code is in
`RegisterCodegenUnboxedKernelsEverything.cpp`:

```cpp
static auto success_with_kernel_reg = register_kernels(kernel_span);
```

This line runs before `main()` only if `__libc_init_array()` is called during
startup. `__libc_init_array` iterates the `.init_array` section (which
contains pointers to all global constructors) and calls each one.

Without the call to `__libc_init_array`, the kernel registry is empty and
every `load_method` call fails immediately.

**Fix:** Call `__libc_init_array` in `Reset_Handler` before `main`:

```asm
call_init:
    bl __libc_init_array
call_main:
    bl main
```

Also requires `.init_array` and `.fini_array` sections in the linker script
(see `stm32f407.ld`).

Also requires `--whole-archive` when linking `executorch_selected_kernels`
(see Gotcha #9).

---

### Gotcha 4: -nostartfiles + _init/_fini Stubs Required

**Symptom:** After adding `bl __libc_init_array`, program crashes inside
`__libc_init_array` at an address beyond the `.text` section. Backtrace shows
`_init()` at a high address falling through into `_fini()` and then into
unmapped memory.

**Cause:** GCC's startup files `crti.o` and `crtn.o` provide `_init` and
`_fini` as "section fragments" — `crti.o` provides the prologue of `_init`
(push registers, no return), and `crtn.o` provides the epilogue (`bx lr`).
When only `crti.o` is linked (which is the default with `-specs=nano.specs`),
`_init` has a `push` but no matching `bx lr`, so it falls through into
`_fini` and beyond.

`__libc_init_array` calls `_init()` first, then iterates `.init_array`, then
calls `_fini()`. Without a proper `_init`, it crashes before reaching the
constructors.

**Fix:** Use `-nostartfiles` to exclude `crti.o`/`crtn.o` entirely, and
provide minimal `_init`/`_fini` stubs in the startup assembly:

```asm
.section .text._init
.thumb_func
.global _init
.type _init, %function
_init:
    bx lr
.size _init, .-_init

.section .text._fini
.thumb_func
.global _fini
.type _fini, %function
_fini:
    bx lr
.size _fini, .-_fini
```

In `CMakeLists.txt` use `target_link_options` (not `CMAKE_EXE_LINKER_FLAGS`)
to apply `-nostartfiles` reliably:

```cmake
target_link_options(firmware.elf PRIVATE
    -nostartfiles
    -T${CMAKE_SOURCE_DIR}/stm32f407.ld
    -Wl,--gc-sections
    -lc -lm -lgcc
)
```

### Gotcha 5: newlib Reentrant Structure Must Be Initialized

**Symptom:** After fixing `__libc_init_array`, crashes in `snprintf` called
from `Method::resolve_operator`. The crash is inside `_svfprintf_r` in
newlib's stdio.

**Cause:** newlib's `snprintf` uses a thread-local reentrant structure
(`_impure_ptr`) that contains `FILE` stream state, locale data, and error
buffers. On bare-metal with `-nostartfiles`, this structure is never
initialized. The first call to `snprintf` dereferences an uninitialized
`FILE*` and crashes.

ExecuTorch calls `snprintf()` in `Method::resolve_operator()` to build
operator name strings for registry lookup. This is not optional — it happens
unconditionally.

**Fix:** Call `_REENT_INIT_PTR(_impure_ptr)` before `__libc_init_array`:

In `syscalls.c`:
```c
#include <reent.h>
void init_newlib(void) {
    _REENT_INIT_PTR(_impure_ptr);
}
```

In `startup_stm32f407.s`:
```asm
call_init_newlib:
    bl init_newlib
call_init:
    bl __libc_init_array
```

### Gotcha 6: newlib memcmp/memcpy/memset Cause Unaligned Faults

**Symptom:** Program crashes in `memcmp` during `ExtendedHeader::Parse`. CFSR
shows UNALIGNED fault, or the function is called with a valid pointer but
crashes inside the newlib implementation.

**Cause:** newlib's optimized `memcmp` uses 32-bit word reads for
performance. On Cortex-M4 with default settings, unaligned 32-bit reads
cause a UsageFault (CFSR UNALIGNED bit). While the specific pointer (buffer +
8) is 8-byte aligned, the newlib implementation has additional alignment
requirements or internal behavior that triggers this fault.

**Fix:** Override `memcmp`, `memcpy`, and `memset` with byte-by-byte
implementations in `syscalls.c`. These are safe for any alignment and the
performance cost is negligible for ExecuTorch's small internal uses.

```c
int memcmp(const void* s1, const void* s2, size_t n) {
    const unsigned char* p1 = (const unsigned char*)s1;
    const unsigned char* p2 = (const unsigned char*)s2;
    while (n--) {
        if (*p1 != *p2) return (int)*p1 - (int)*p2;
        p1++; p2++;
    }
    return 0;
}
```

Similarly override `memcpy` and `memset`.

**Note:** `-mno-unaligned-access` is also set in the compiler flags, which
prevents the compiler from generating unaligned accesses in application
code. However this does not affect pre-compiled newlib — the override is
still needed.

### Gotcha 7: Model Array Must Be 16-Byte Aligned

**Symptom:** `Program::load` returns error code `0x12` (`InvalidArgument`).

**Cause:** ExecuTorch's FlatBuffer parser checks that the program data
pointer is aligned to `alignof(std::max_align_t)` (typically 8 or 16 bytes on
ARM) before parsing. The `xxd -i` generated array is `unsigned char[]` with
no alignment guarantee.

**Fix:** Post-process the `xxd` output in `CMakeLists.txt` to add
`__attribute__((aligned(16)))`:

```cmake
string(REPLACE
    "unsigned char tiny_model_pte[]"
    "__attribute__((aligned(16))) const unsigned char tiny_model_pte[]"
    XXD_OUTPUT "${XXD_OUTPUT}")
```

### Gotcha 8: et_pal_emit_log_message Must Be Stubbed

**Symptom:** When an operator is not found, the program crashes in
`fprintf` inside `et_pal_emit_log_message` (the ExecuTorch log output
function).

**Cause:** The default `et_pal_emit_log_message` in
`executorch/runtime/platform/default/posix.cpp` uses `fprintf(stderr, ...)`
which requires working `FILE*` infrastructure. Even with `-DET_LOG_ENABLED=0`,
some log calls in `operator_registry.cpp` bypass this flag.

**Fix:** Provide a no-op override in `syscalls.c`:

```c
void et_pal_emit_log_message(
        long timestamp, int level,
        const char* filename, const char* function, unsigned long line,
        const char* message, unsigned long length) {
    (void)timestamp; (void)level; (void)filename;
    (void)function;  (void)line;  (void)message; (void)length;
}
```

### Gotcha 9: --whole-archive Required for Op Registration

**Symptom:** `load_method` returns `OperatorMissing` (0x14) even though the
kernel library is linked.

**Cause:** C++ static initializers (global constructors) that register ops
into the kernel registry are in object files with no symbols directly
referenced by `main`. The linker's default behavior is to skip unreferenced
object files from static libraries. The registration code is silently
discarded.

**Fix:** Wrap `executorch_selected_kernels` in
`--whole-archive`/`--no-whole-archive`:

```cmake
target_link_libraries(firmware.elf PRIVATE
    -Wl,--whole-archive
    executorch_selected_kernels
    -Wl,--no-whole-archive
    portable_kernels
    executorch
    executorch_core
    ...
)
```

Only `executorch_selected_kernels` needs `--whole-archive`. Putting
`portable_kernels` (148MB) under `--whole-archive` causes a 10MB+ binary that
exceeds flash capacity.

---

### Gotcha 10: Use executorch_selected_kernels, Not portable_ops_lib

**Symptom:** Binary exceeds flash (10MB+ overflow) when `portable_ops_lib` is
used with `--whole-archive`.

**Cause:** `portable_ops_lib` contains the registration for ALL portable ops
(hundreds of operators). With `--whole-archive` this pulls in the
registration and implementation for every op, totaling ~10MB.
`EXECUTORCH_SELECT_OPS_LIST` affects `executorch_selected_kernels`, not
`portable_ops_lib`.

**Fix:** Build and link `executorch_selected_kernels` instead:

```bash
cmake --build ~/executorch/executorch-build/cortex-m4 \
  --target executorch_selected_kernels -j$(nproc)
```

The library is at:
`~/executorch/executorch-build/cortex-m4/libexecutorch_selected_kernels.a`

With 3 ops selected, the resulting binary is ~300KB text — fits easily.

### Gotcha 11: .ARM.exidx Section Required

**Symptom:** Linker error: `undefined reference to '__exidx_start'`.

**Cause:** libgcc's ARM exception unwinding code (`libunwind`) requires
`__exidx_start` and `__exidx_end` symbols even when `-fno-exceptions` is
used. The `.ARM.exidx` section in the linker script defines these symbols.

**Fix:** Add to linker script:

```ld
.ARM.exidx :
{
    __exidx_start = .;
    *(.ARM.exidx*)
    *(.gnu.linkonce.armexidx.*)
    __exidx_end = .;
} > FLASH
```

### Gotcha 12: Thumb Bit Must Be Set in Vector Table

**Symptom:** CPU immediately faults on reset before executing any
application code. GDB shows `xPSR: 00000000` (Thumb bit not set).

**Cause:** All Cortex-M code runs in Thumb mode. Vector table entries must
have their LSB set to 1 to indicate Thumb mode. Without `.thumb_func` before
the handler definitions, the assembler generates even addresses for function
symbols, and the CPU attempts to execute in ARM mode (illegal on Cortex-M)
and immediately faults.

**Fix:** Use `.thumb_func` before every function defined in assembly:

```asm
.thumb_func
.type Reset_Handler, %function
Reset_Handler:
    ...
```

Verify the vector table has odd addresses:
```bash
arm-none-eabi-objdump -s --section=.isr_vector build/stm32/firmware.elf | head -5
# Reset vector should be 0x080005c1 (odd), not 0x080005c0 (even)
```

### Gotcha 13: xxd Must Run From models/ Directory

**Symptom:** Compiler error `'tiny_model_pte' was not declared`.

**Cause:** `xxd -i file.pte` uses the input filename (with path) as the C
variable name, replacing non-alphanumeric characters with `_`. Running
`xxd -i models/tiny_model.pte` generates a variable named
`_home_user_project_models_tiny_model_pte` instead of `tiny_model_pte`.

**Fix:** In `CMakeLists.txt`, use `cmake -E chdir` to run xxd from the
`models/` directory:

```cmake
execute_process(
    COMMAND ${CMAKE_COMMAND} -E chdir ${CMAKE_SOURCE_DIR}/models
        xxd -i tiny_model.pte
    OUTPUT_VARIABLE XXD_OUTPUT
    ...
)
```

### Gotcha 14: SELECT_OPS_LIST Uses .out Variants

**Symptom:** `EXECUTORCH_SELECT_OPS_LIST="aten::mul.Tensor,aten::add.Tensor"`
generates a registration file with only 1 kernel (or wrong kernels).

**Cause:** ExecuTorch's portable kernels are registered under the `.out`
variant names (e.g. `aten::mul.out`), not the `.Tensor` variant names. The
`.Tensor` variants appear in the PyTorch edge IR but are lowered to `.out`
variants for ExecuTorch execution.

**Fix:** Use `.out` variants in `EXECUTORCH_SELECT_OPS_LIST`:
```
-DEXECUTORCH_SELECT_OPS_LIST="aten::mul.out,aten::add.out,dim_order_ops::_to_dim_order_copy.out"
```

Verify by checking the generated registration file after ExecuTorch builds:
```bash
grep "Kernel(" ~/executorch/executorch-build/cortex-m4/executorch_selected_kernels/RegisterCodegenUnboxedKernelsEverything.cpp
```
Should show one `Kernel(` line per op.

### Gotcha 15: -fno-pic -fno-pie in Toolchain File (needs verification)

**Status:** Added during debugging of GOT-related crashes. Whether this is
strictly necessary or whether fixing Gotcha #2 (GOT ordering) alone is
sufficient has not been isolated.

**What it does:** Prevents the compiler from generating position-independent
code that accesses globals via GOT-relative addressing.

**Current state:** Both the GOT ordering fix AND `-fno-pic -fno-pie` are
present. To determine if `-fno-pic -fno-pie` is independently required,
remove it from the toolchain file and rebuild. If the GOT ordering fix alone
is sufficient, this flag can be removed.

---

### Gotcha 16: snprintf Override (needs verification)

**Status:** Added after `_REENT_INIT_PTR` alone was insufficient to prevent
snprintf crashes in some test scenarios.

**What it does:** Replaces newlib's `snprintf` with a bare-metal safe
implementation that does not use `FILE*` infrastructure.

**Current state:** Both `_REENT_INIT_PTR` (Gotcha #5) and the `snprintf`
override (in `syscalls.c`) are present. Whether both are needed or
`_REENT_INIT_PTR` alone is sufficient has not been isolated.

To verify: remove the `snprintf`/`vsnprintf` overrides from `syscalls.c`,
rebuild, and test. If it still runs correctly, the overrides are not needed.
